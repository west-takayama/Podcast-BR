# 🎙️ Podcast BR

スマホ完結型のポッドキャスト運営ツール。収録した **.WAV をアップロードするだけ**で、整音・MP3変換から、タイトル・説明文・ショーノート・チャプター・SNS告知文の生成までを自動で行い、Spotify for Creators への投稿を最短化します。

## 仕組み

```
[スマホブラウザ PWA]
  ① 収録した音声を選択(WAV / MP3 / M4A / AAC など)
  ② 端末内で 解析 → 整音 → MP3変換(サーバー不要・Web Worker)
  ③ Gemini API(無料枠)で文字起こし+メタデータ一括生成
  ④ ワンタップコピー + MP3 ダウンロード + 履歴保存
  → Spotify for Creators アプリに貼り付けて投稿(約30秒)
```

処理中は全体の進捗率と**残り時間の目安**が表示されます。残り時間は端末性能や回線速度を事前に決め打ちせず、実際の進み具合から毎回引き直しています。

- **完全無料で運用可能**: 静的サイト(GitHub Pages)+ Gemini API 無料枠。サーバー費用ゼロ。
- **プライバシー**: 音声処理はすべて端末内で完結。音声は Google の Gemini API 以外へ送信されません。API キー・履歴は端末内にのみ保存されます。
- **Spotify for Creators に投稿 API がないため**、最後の投稿操作のみ Creators アプリで行う半自動方式です。

## 生成される素材

| 項目 | 内容 |
| --- | --- |
| タイトル案 | 切り口を変えた3案。タップで採用タイトルを記録 |
| 説明文 | 冒頭で核心を伝え、聴きどころを列挙。文字数は設定で調整可 |
| 説明欄まとめて貼り付け | 説明文+チャプター+ハッシュタグを1つに連結(Creators に一度で貼れる) |
| ショーノート | 話題の流れを追える Markdown 箇条書き |
| チャプター | `MM:SS` 形式の話題の切り替わり |
| ハッシュタグ / 検索キーワード | 日本語圏で実際に使われる語 |
| SNS告知文 | X(140字以内)/ Instagram / メール・ブログ用の3種 |
| 全文書き起こし | 時刻と話者付き。必要なときだけ作成 |
| 切り抜き候補 | 単体で面白い30〜60秒を3つ。見出し付きで縦型動画に書き出せる |
| ショート(動画から) | 動画を上げると、ショート向きの区間を自動で探して縦型に切り出す |
| 今回の出演者 | 説明文の頭に「出演: ◯◯・△△」を入れ、聞く前に誰の回か分かるようにする |

| 人ごとの音量合わせ | 参加者ごとの音声をまとめて選ぶと、音量を揃えて1本にする |
| 人ごとの音色合わせ | マイクや部屋の違いによる声色の差を寄せる(切り替わりの違和感を消す) |

## 対応する入力形式

WAV / MP3 / M4A / AAC / OGG / FLAC など、端末が再生できる音声はそのまま使えます。**Zoom や Discord の通話録音、スマホの録音アプリの出力を変換せずに投げ込めます。**

WAV は専用の速い経路を通ります(バイト列を TypedArray で直接読めるため)。それ以外はデコーダを通すので、同じ長さでも時間がかかります。実測(2分の音声・全工程):

| 入力 | 所要時間 |
| --- | --- |
| WAV | 1.6秒 |
| MP3 | 7.0秒 |

圧縮音声は解析のたびにデコードし直すため差が出ます。60分なら WAV 約1.2分に対し MP3 は約3.5分の見込みです。

## 人ごとに分かれた音声を揃えて1本にする

**オンライン収録では、参加者ごとに別ファイルで書き出せることが多い**(Riverside / Zencastr / Zoom など)。分かれていれば被りも混ざりも無いので、**それぞれ別々に測って正確に合わせられます**。「片方だけ声が小さい」を推測なしで直せます。

作成画面でまとめて選ぶと、変換の前に音量を測って合わせ方を出します。

```
spk-a.wav   -6.8dB    測った音量 -15.2 LUFS ・ 自動 -6.8dB ・ 20分13秒
spk-b.wav   +6.8dB    測った音量 -28.9 LUFS ・ 自動 +6.8dB ・ 20分13秒
```

スライダーで**人ごとに手動の増減も足せます**(±12dB)。変換の前に決めるのは、あとから直すと数分かけた処理をやり直すことになるためです。測るだけならエンコードが走らないので軽く済みます(10分の素材で3秒)。**測った結果はそのまま変換へ渡すので、測り直しは起きません**(10分の素材で 2.3秒、60分なら約14秒の短縮)。

### 音色(声の質)も揃える

音量が揃っても、**マイクと部屋が違えば聞こえ方は揃いません**。片方はこもって、片方は細い。会話で切り替わるたびに耳が調整を強いられるので、長く聴くと疲れます。

人ごとに分かれていれば、それぞれの周波数バランスを測って寄せられます。1オクターブ刻みの7帯域(125Hz〜8kHz)で測り、**全員の平均へ**向けて最大 ±6dB 補正します。「相手に似せる」だけなので元より良い音にはなりませんが、**揃っていないことによる粗さは消えます**。

選択画面に補正量が出るので、要らなければ切れます。

```
   Hz    spk-a   spk-b
  125    -2.4    +2.4
  250    -1.9    +1.9
  ...
   8k    +2.7    -2.7
```

出来上がった MP3 を鳴らし直し、話者ごとの帯域バランスを測った結果:

| 素材 | 補正なし | 補正あり |
| --- | --- | --- |
| 現実的なマイク2本ぶんの差 | 5.4dB | **0.8dB** |
| 極端に違う2人 | 14.3dB | **3.9dB** |

極端なほうが埋まりきらないのは ±6dB の上限に当たるためです。7dB 以上の差はマイクか部屋を直したほうが早い、という判断です。

#### 音色を直すと音量が動く

低音を削って高音を足せば、形は揃っても全体の音量は下がります。音量合わせは音色を直す**前**に決めているので、放っておくと**せっかく揃えた2人が最大 5.7dB ずれます**(実測)。

測り直すにはもう一度ファイル全体を読む必要があるため、代わりに**測ってある帯域ごとの中身**から動く量を見積もって差し引いています。人の耳の効き方(K特性)で重みを付けるので、ラウドネスの動きに対応します。見積もりの誤差は **0.16dB**、差し引いたあとに2人の間へ残るずれは **0.27dB** でした。

#### 狙った通りの形にする

オクターブ間隔で並べたフィルタは裾が隣まで届くので、「+3dB にしたい」と指定してそのまま並べると、隣からの足し込みで **0.85dB ずれます**。作った形を測っては差を戻す、を繰り返して合わせ込んでいます(ずれ **0.01dB**)。

#### 長い回でも待たされない

帯域ごとの測定は重く、全部を通すと10分の素材で **7.1秒**、60分なら40秒を超えます。音色はマイクと部屋と声で決まるもので回の途中で変わらないため、**全体から等間隔に 2分半ぶんだけ**拾って測ります(頭だけを見ると、相手が喋っている間ずっと黙っている収録で外すため)。10分で **1.8秒**、60分でも **1.9秒**に収まります。

間引きの位置は黄金比でずらしています。毎回同じ位置を取ると、会話の周期と噛み合ったときにいつも同じ場面(喋り始めばかり/沈黙ばかり)を拾うためです。前半と後半で声色を変えた素材で、全部通した場合との差は **0.43dB** でした。

#### 環境音を持ち上げない

その帯域に**声が入っているか**は、「声が出ている間」と「静かな間」を比べて判断します。差が小さい帯域は空調やパソコンの音しか無いので、持ち上げません(下げるのは常に安全なので許します)。

「いちばん大きい帯域より何dB下か」で決める手もありますが、それだと低音の多い声ほど高域を諦めることになります。

### 「あまり喋らない人」が持ち上げられないか

人ごとのファイルは**大半が沈黙**です。もし測定が沈黙に引きずられると、喋る量が少ない人ほど小さく測れて、その分だけ余計に持ち上げられます。

BS.1770 の2段ゲート(絶対 −70 LUFS / 相対 −10 LU)がこれを防ぎます。同じ声の大きさのまま喋る割合を **91% → 10%** まで変えて測ったところ、ずれは **0.04dB** でした。検証はテストに入れてあります。

(なお、0.5秒だけ喋るような極端な信号では 1.9dB ずれます。400ms のブロックに対して発話が短すぎ、ほとんどが立ち上がり・立ち下がりになるためです。実際の会話では起こりません。)

### 合わせ先は平均にする

誰か一人を基準にすると他の全員が片方向へ動くことになり、移動幅の上限(±12dB)に当たって差が埋まりきりません。平均なら両側へ分かれるので、同じ上限でより広い差を吸収できます。

| 2人の差 | 大きいほうを基準 | 平均を基準 |
| --- | --- | --- |
| 14dB | +12dB(上限)→ 2dB 残る | ±7dB → **完全に揃う** |
| 20dB | +12dB(上限)→ 8dB 残る | ±10dB → **完全に揃う** |
| 24dB | +12dB → 12dB 残る | ±12dB(上限)→ 差は半分に |

最終的な音量はこのあとの −19 LUFS への調整で決まるので、ここで決めているのは**人と人の相対差だけ**です。どちらを基準にしても仕上がりの環境音の量は変わりません。上限があるのは、ほとんど喋っていないファイルを無理に持ち上げてリミッターを働かせすぎないためです。

### 全部をメモリに載せない

60分ステレオを2本展開すると 2GB を超えてスマホでは落ちます。読み手を**少しずつ交互に進めながら足して**います。読み手側は「受け取り終わった」と言われるまで次へ進まないので、バッファを上書きされる心配も、余分に溜め込む必要もありません。

合成したものは既存の読み手と同じ形で振る舞うため、**このあとの変換の流れ(解析2回 → 整音 → −19 LUFS → リミッター → MP3)は一切変わりません**。

- ブロックの区切りが揃っていなくても正しく足せます(WAV とデコーダ経由で長さが違うため)
- 途中で退出して**短いファイルがあっても**、足りない分は無音として扱います
- モノラルのトラックは左右へ同じだけ入れます(片側に寄せない)
- **サンプリングレートが違う場合はエラーにします。** 混ぜると速度がずれるので、同じ設定で書き出し直してもらいます

検証は、声の大きさを 14dB 変えた2ファイル(140Hz と 220Hz)を通し、**出来上がった MP3 を鳴らし直して両方の成分を測っています**。結果は差 **0.1dB** まで揃いました。

## 1本のマイクで2人を録っている場合

**1本に混ざった音から声を分離することはできません。** 機械学習のモデルが要る領域で、スマホのブラウザで動く規模ではありませんし、同時に喋った部分はいまでもきれいには分かれません。「端末内で完結・無料」という前提を捨てることになります。

分かれた状態で書き出せないか、まず収録側の設定を確認するのが近道です。

## 2人を別マイクで録っている場合

設定の「2人を別マイクで左右に分けて録っている」を有効にすると、**ノイズ低減をチャンネルごとに独立して行います。** 話していない人のマイクの環境音を個別に抑えられます。

実測では、片方が話している間の無音側マイクの環境音が **9.2dB** 下がり、話している側は無加工のままでした。

左右で同じ音を録っている素材(1本のマイクや環境音)で有効にすると定位が崩れるため、既定は無効です。

なお話し終わった直後は減衰しません。リリース(150ms)を設けて語尾を切らないようにしているためで、意図した挙動です。

## 今回のパーソナリティを、聞く前に分かるようにする

回によって出る人が変わる番組では、**再生を押す前に「今日は誰の回か」が分からない**のが困ります。Spotify の一覧で再生前に見えるのは、タイトルと説明文の頭だけです。

作成画面に「🎤 今回の出演者」を置きました。打ち込むと、**説明文とまとめて貼り付けのいちばん上**に1行入ります。

```
出演: たかやま・にし・ゲスト 山田さん

今回は新しいマイクを買った話をしました。
...
```

### AI に書かせない

説明文を書くのは AI ですが、**この行だけはアプリが必ず足します**。AI に任せると名前が落ちたり、言い換えられたりします。回ごとに変わるものを取り違えるのは、番組として誠実ではありません。

AI には「今回は誰が出ているか」だけ伝えて、**自分では出演者の行を書かないよう**頼んでいます。それでも書いてきた場合は、こちらの行で置き換えます(手で入れたほうが正しいため)。

### 打ち忘れても大丈夫

結果画面と履歴から、**あとから足せます**。変換はやり直しません。直せば説明文とまとめて貼り付けにその場で反映され、消せば行ごと消えます。何度足しても二重になりません。

### 打ちやすさ

区切りは読点・中黒・カンマ・改行のどれでも受け付けます。「ゲスト 山田さん」のように**名前の中に空白が入っても割りません**(区切りとみなすのは空白2つ以上)。表示は中黒で揃えます。

| 打ったもの | 出るもの |
| --- | --- |
| `たかやま、にし` | 出演: たかやま・にし |
| `たかやま・にし` | 出演: たかやま・にし |
| `たかやま, にし` | 出演: たかやま・にし |
| `たかやま、ゲスト 山田さん` | 出演: たかやま・ゲスト 山田さん |

前回入力した内容が次回の初期値に入るので、同じ顔ぶれが続くときは打ち直さずに済みます。中断から復帰したときも、打ち込んだ内容は残ります。

## シリーズの一貫性

直近8回のタイトルをプロンプトに渡します。「#12」「第12回」のような番号の付け方が使われていれば同じ体裁で続きの番号にし、使われていなければ番号を付けません。過去回と同じ切り口の繰り返しも避けさせています。

## チャプター時刻の精度

AI が音声から読み取る時刻は数秒から十数秒ずれることがあります。ずれたチャプターは無いより悪いので、**端末側の解析で補正**しています。

1. 変換時に「一定以上の沈黙が終わって声が戻った位置」を検出する(出力の時間軸で数えるため、無音カットを有効にしていても再生位置と一致します)
2. その一覧を候補としてプロンプトに渡し、原則そこから選ばせる
3. 返ってきた時刻を、20秒以内にある最も近い候補へ吸着させる

補正した件数と最大補正量は結果画面に表示されます。冒頭の `00:00` は動かしません。候補から遠い時刻はAIの判断を尊重してそのまま残します。

## 全文書き起こし

時刻と話者付きの書き起こしを作れます。検索対策・アクセシビリティ・引用探しに使えます。

メタデータとは**別の呼び出し**にしています。1回のレスポンスに詰め込むと出力上限に当たって全体が壊れるためです。また必要なときだけ作れば無料枠を節約できます。

設定で話者の呼び名を入れておくと「A」「B」ではなく具体名になります。聞き取れない箇所は推測で埋めず「(聞き取り不明)」とするよう指示しています。

設定の「この番組でよく出る言葉」に番組名・相方の名前・造語などを入れておくと、その表記を優先させます。AI は**その番組にしかない言葉**をよく聞き間違えるためで、書き起こし・字幕・メタデータ生成のすべてで使います。

## 「次の回」ページ(次に話すお題)

**これまでに話したことをもとに、次のお題を考えます。**

### やめたこと:少ないデータからの助言

当初は投稿間隔・長さの推移・タイトルの癖から助言も出していました。**やめました。**

実データ(30日・1日あたり平均16.9回・標準偏差7.8)で検定したところ、こうなったためです。

| 見ていたもの | 結果 |
| --- | --- |
| 土日 vs 平日 | 12.4 vs 18.5、**p=0.055** |
| 水木 vs それ以外 | 21.0 vs 15.1、**p=0.063** |
| 後半15日 vs 前半15日 | 17.3 vs 16.5、**p=0.824** |

どれも偶然で普通に起きる範囲でした。さらに、**上位6日(配信日と思われる)を除くと曜日差は −6.2 → +1.7 に消えます。** 「水木が強い」ではなく「配信した日は伸びる」だけで、投稿曜日を変える判断には使えません。

1日十数回という規模では、日を単位にした比較はほぼ何も検出できません。**偶然と区別がつかないものを言い切ると判断を誤らせる**ので、数えるだけで確かなこと(何を話してきたか)に絞りました。

### 残していること:話題の棚卸し

| 出しているもの | 何の役に立つか |
| --- | --- |
| よく扱う話題 | 番組の軸。2回以上出た語だけ |
| 最近出てきた話題 | 直近5回で**初めて**出た語 |
| しばらく触れていない話題 | 2回以上扱ったのに直近5回では出ていない語 |

これは統計的な推定ではなく、**自分たちが何を話したかの記録**です。お題を考える材料として素直に使えます。

語はキーワードとハッシュタグをまとめて数えます。`#カメラ` と `カメラ` は同じ語(全角英数も半角に寄せる)、1文字の語は落とす、同じ回に何度出ても1回、という扱いです。

「最近出てきた話題」は**初出**で判定します。「最後に出たのが直近」で判定すると昔からある語まで入り、「よく扱う話題」と丸かぶりになりました。

### 聴かれ方は分かりません

**Spotify for Creators に再生数を取れる公開 API はありません。** どの回が伸びたかはこのツールからは分からないので、画面に明記しています。AI への指示文にも「**手元にない情報を根拠にしない**」と入れています。

なお公式の CSV 書き出しはありますが、取れるのは**番組全体の日ごとの合計**でした(エピソード別が要る)。加えて、`Spotifyの再生数`(30秒以上聴かれた回数)と `Spotify以外のダウンロード数`(落とされただけで聴かれたとは限らない)は**単位が違うので足し引きできません**。

### お題の提案

送るのは**タイトル・日付・要約・チャプターの見出し**と話題の棚卸しだけ。**音声も書き起こしの本文も送りません**(実測で 1622文字)。

- **過去回の続きを優先する。** 結論が出ないまま流れた話は、それだけで1回になる
- **しばらく触れていない話題**は、前と違う角度で話し直す
- 番組の色から外れた一般論のお題は出さない
- 今日の日付を渡して、時期が効くお題があれば入れさせる

案ごとに、**お題・なぜ今なのか・切り口3つ・冒頭2秒の掴み・つながる過去回**が付きます。掴みはそのままショートの見出しに使えます。案出しなので温度は 0.9 と高めです(固くすると似た案が並ぶため)。

## 過去回の横断検索

回が溜まると「あの話、どの回だっけ」が思い出せなくなります。**一番おいしい30秒は最新回にあるとは限らない**ので、探せないと過去回はそのまま埋もれます。

履歴の先頭で言葉を入れると、**その場面の位置まで**出ます。結果を押すとその回が開き、**見つけた場面が切り抜き候補の先頭に入る**ので、そのまま縦型ショートにできます(発話の3秒前から40秒)。回が増えるほど、切り抜きの持ち球が増えていきます。

探す順番は次のとおりです。

1. **書き起こし** — 切り抜きに使えるのはここだけなので最優先。1回につき最大8件
2. 書き起こしが無い回は、**タイトル → チャプター → 説明・要約**の順で、せめてどの回かが分かるように

書き起こしを持っている回数は画面に出します(「全12回のうち5回に書き起こしがあり、場面の位置まで引けます」)。

端末の容量のため、**音声は直近5回ぶんだけ**残しています。それより前の回は本文と書き起こしだけが残りますが、**切り抜きの欄で MP3 を選び直せば、古い回も縦型動画にできます。** 選ぶのは収録時の元ファイルではなく、**このアプリで書き出した MP3** です(時刻はそちらを基準にしているため)。

明らかに短いファイル(別の回や、切り抜きたい位置に届かないもの)を選んだ場合は、書き出す前に警告を出します。

### 表記のゆれ

カタカナ⇔ひらがな、全角⇔半角、大文字⇔小文字は畳みます。**ただし漢字とかなは別物のまま**です(「ねぎ塩」と「ねぎしお」は繋がりません)。繋ぐには読みの辞書が要るので、いまは**画面にその旨を書いて、書き方を変えてもらう**方針にしています。空白で区切ると、その全部を含む文だけを出します(AND)。

## 収録の診断

処理と同時に、生の入力(整音を通す前)を検査します。問題があれば結果画面の先頭に、次回の収録で直すための助言を添えて出します。何も問題がなければ何も出ません。

| 検出するもの | なぜ重要か |
| --- | --- |
| 左右の位相が逆 | モノラルに落とすと打ち消し合って音がほぼ消える。気づかず公開すると無音のエピソードになる |
| 片チャンネルが無音 | 片方のマイクが録れていない。ステレオで出すと片側が無音になる |
| クリッピング(歪み) | 録音レベルが大きすぎて波形が振り切れている。後から取り除けない |
| 直流オフセット | 波形の中心がずれて音量の余裕が減る(低域カットで補正される) |
| 録音レベルが低い | 目標まで大きく持ち上げるため、環境音も一緒に持ち上がる |
| 環境音が大きい | 声と環境音の差が18dB未満。ノイズ低減で抑えても限界がある |

クリッピングと直流オフセットは整音を通すと見えなくなるため、判定はハイパスもノイズ低減も通す前の波形に対して行います。環境音の判定は「声が鳴っている区間の RMS」と比較します(全体の RMS と比べると、沈黙の多い回ほど声が小さく見えて誤検出になる)。

## 混雑(503)は自動で待って投げ直す

Gemini は混雑時に `503 UNAVAILABLE`(This model is currently experiencing high demand)を返します。**利用量とは無関係で、待てば直る種類の応答**です。無料枠は空いている容量を分けてもらう扱いのため、混雑時ほど当たりやすくなります。

そのため 500 / 502 / 503 / 504 は **3秒 → 8秒 → 20秒**と間を空けて自動で投げ直します。待っている間は理由を画面に出します。送信(アップロード)も同じ扱いです。数十MBの送信を混雑ひとつで捨てないためです。

429(レート制限)は自動再試行しません。無料枠の上限に当たっている状態で急いで投げ直しても待ち時間が延びるだけだからです。

3回の再試行でも回復しない場合は、生の JSON ではなく「混雑しているので数分待ってから再試行してください」と伝えます。原因が Google 側にある以上、JSON を見せても打つ手は変わりません。

## 失敗しても変換をやり直さない

無料枠のレート制限(429)や通信の切断は生成の途中で起こります。変換は数分かかるので、そのたびに捨てるのは損が大きい。

そのためエラー画面には**「生成だけやり直す」**が出ます。変換結果は端末内に持っているので、押せば数十秒で終わります。アップロードまで済んでいれば送信もやり直しません。変換済み MP3 のダウンロードリンクも同じ場所に出るので、文章は諦めて音声だけ使うこともできます。

## 中断しても変換は残る

変換が終わった時点で、その結果を端末内(IndexedDB)に控えます。生成の途中でアプリが落ちても、他のアプリに切り替えてブラウザに止められても、次に開いたときに**変換をやり直さずに文章の生成から続けられます**。

復帰カードには、ファイル名・長さ・変換した時刻・控えが使っている容量を出します。送信まで済んでいた場合は送信も省きます(「送信も済み」と表示)。文章を諦めるなら MP3 だけ取り出せますし、破棄すれば容量が戻ります。

控えは履歴に保存できた時点で消えます。新しい音声を選んだときや「次のエピソードを処理する」を押したときも消えます。常に1件だけです。

## オフラインでも使える

初回に開いた時点で、アプリ本体と WASM エンコーダを端末にキャッシュします(Service Worker)。以降は圏外でも起動でき、**変換・整音・タグ付けは通信なしで完走します**(すべて端末内の処理)。文章生成だけは Gemini への通信が必要です。

起動時に毎回ダウンロードを待たなくなるため、2回目以降の立ち上がりも速くなります。

### 新しい版への切り替え

新しい版は**待機させ、勝手に切り替えません**。画面上部に「🎉 新しい版があります」と出るので、押したときだけ切り替えて読み直します(処理中は押せません)。

当初は `install` で `skipWaiting()` していましたが、**動いているページが使う資材を消してしまい、利用者の端末で "Load failed" が出ました。** 新しい世代のキャッシュを作った直後に古い世代を消すため、古いページがあとから読むファイル(遅延読み込みのチャンクなど)が、キャッシュにもサーバー(ハッシュ付きの旧ファイル名は消えている)にも無くなるためです。

いまは古いキャッシュを消すのは、利用者が更新を押して新しい版が activate したときだけです。検証は「旧版を開いた状態で新版をデプロイし、資材が読めるままか」を実際に確かめています。

#### 初回に画面が作り直されていた

交代(`controllerchange`)が起きたら読み直す、という作りにしていました。コメントには「押した直後にしか起きない」と書いてありましたが、**間違いでした**。

初めて開いたときにも交代は起きます。新しく入った Service Worker が `activate` で `clients.claim()` を呼び、開いているページを引き取るためです。その結果、**初回だけ数秒後に画面が作り直され、打ちかけの API キーも、選んだ直後の音声も消えていました。**

いまは2つとも満たしたときだけ読み直します。

- ページを読み込んだ時点で既に前の版に面倒を見てもらっていた(初回は該当しない)
- 利用者が「更新する」を押した

検証は、初回に開いてキーを打ち、6秒待っても画面が作り直されず入力が残っていることを実機同様のブラウザで確かめています(直す前は 2回読み込まれ、入力が消えることも再現済み)。

## 音声を送り直さずに作り直す

Gemini の Files API は音声を48時間保持します。この間は**変換もアップロードもせずに文章だけ作り直せます**。

タイトルの温度感が合わないときや、設定でトーン・文字数を変えて試したいときに、毎回 WAV を選び直す必要がありません。期限切れの場合はその旨を表示します。

## 読み込んだ写真は端末内に残る

読み込んだ写真は、**MP3 のカバーと縦型ショートの背景**で共有します。以前はタブを切り替えるだけで消えていました(画面の状態としてしか持っていなかったため)。いまは端末内(IndexedDB)に控え、開き直しても残ります。「この画像に文字を入れる」の選択も一緒に覚えます。

ただし**次の回には持ち越しません**。写真はその回の情景を写したものなので、別の話に付けると内容と合わなくなるためです。新しい音声を選ぶか「次のエピソードを処理する」を押した時点で控えごと消えます。

読み戻したときは MP3 のカバーを付け直しません。開いただけで処理が走ってしまうので、実際に読み込む操作をしたときだけ付け直します。

## 生成結果の編集

説明文とショーノートはその場で手直しでき、編集内容は履歴にも保存されます。コピーボタンは編集後の文をコピーします。

## 「ショート」ページ(動画から作る)

**撮った動画をそのまま投げ込むと、ショートに向いた区間を自動で探して縦型に切り出します。** 収録の回とは独立した別ページです。

```
動画を選ぶ → 音声だけ取り出して Gemini に聴かせる → 候補が3つ出る
→ 選んで「縦型ショートにする」→ その区間を 1080×1920 で書き出す
```

- **動画そのものはどこにも送りません。** 送るのは取り出した音声(32kbps モノラル)だけです
- 音声を取り出すときは**無音カットを必ず切ります**。詰めると映像と音声の時刻がずれるためです
- 映像は元動画から切り出し、短辺に合わせて中央で切ります(横長は左右が切れます)
- 字幕は**選んだ区間の音声だけを切り出して**書き起こします。全編を書き起こすより速く、無料枠も食わず、何より時刻が大きくずれません(→「字幕の精度」)
- 暗幕は上下の帯だけに掛けます。全面に掛けると元の映像が潰れるためで、**動画では映像が主役**です。文字は縁取りで読ませます

### 表紙(カバー画像)を1コマ選んで書き出す

フィードで最初に目に入るのは動画ではなく**1枚の絵**です。先頭のコマがたまたま目を閉じていたり被写体が見切れていたりすると、それだけで見られなくなります。

「🎞 この区間から表紙の候補を出す」で区間の中から6コマを等間隔に取り出し、選んだ1枚を見出し入りの 1080×1920 で書き出します。両端は話の切り替わりに当たりやすいので、内側に寄せて取っています。

**動画そのものには手を入れません。** 静止画を頭に挟むと音とのずれが出ますし、Instagram も YouTube も表紙だけ別の画像を上げられるので、別ファイルにするほうが安全で使い勝手もよいためです。

見た目は動画の1コマと同じ作りにして、番組としての印象を揃えています。ただし表紙では**字幕・波形・残り時間のバーは省きます**(1枚絵に進行状況は要らないので)。

### 字幕は焼き込む前に直せる

AI は**この番組にしかない言葉**をよく聞き間違えます。番組名、相方の名前、造語、お店の名前。「ねぎ塩」が「ねぎ潮」になる類です。動画に焼き込んでしまうと直しようがないので、二重に手を打っています。

**1. 先に登録しておく(設定の「この番組でよく出る言葉」)**

カンマ区切りで入れておくと、書き起こしの指示に「この表記で書く。似た音に聞こえてもこちらを優先する」として渡ります。エピソードのメタデータ生成でも同じ語を使います。**音は近いけれど普通の日本語には無い言葉**ほど効きます。

**2. 焼き込む前に直す**

「📝 先に字幕を作って確認する」を押すと、書き出す前に下書きが出ます。行ごとに文字を直せて、要らない行は消せます。直した内容がそのまま動画に入ります。

書き出しは1本 10秒前後かかるので、「作って → 間違いに気づいて → 作り直す」を繰り返すと時間を食います。先に直せば1回で済みます。直した字幕は使い回されるので、**書き出しのたびに書き起こしを頼み直すこともありません**(無料枠の節約にもなります)。

範囲を前後にずらすと、聴かせる音声そのものが変わるので下書きは作り直しになります。

### 候補をまとめて書き出す

ショートは**数を出したほうが伸びます**。1本が当たるかどうかは出してみないと分からないので、3本出して様子を見るほうが確率が上がります。

「📦 候補をまとめて書き出す」で、候補を順に書き出して一覧に並べます。候補ごとに範囲・字幕・書き出した動画をそれぞれ持っているので、

- 1本だけ範囲を調整して、その本だけ作り直す
- すでに直した字幕はそのまま使う(書き出し済みの本は書き起こしを頼み直さない)
- 済んだ候補には一覧に ✅ が付く

といった使い方ができます。範囲や字幕を変えた候補は、書き出し済みの動画を捨てて作り直しになります(古い動画が残っていると、どちらが最新か分からなくなるため)。

### 読み取りを速くする(AI に聴かせる音声だけを作る)

「作成」の変換は、**配信する音を狙った音量(−19 LUFS)に収める**ために、最大4回ファイルを読みます。

1. ノイズフロアと収録の問題を測る
2. 整音したあとのラウドネスを測る
3. (必要なとき)リミッターで下がる分を試し処理で測る
4. 整音 → 音量調整 → リミッター → MP3 を2本(配信用・AI用)書き出す

ところが**「ショート」ページでは、このうち AI 用の1本しか使いません。** 配信用 MP3 も、測ったラウドネスも、リミッターの結果も、全部捨てていました。

そこでこのページ専用に、**1回読んで1本だけ書き出す経路**を通します。

- 測るための読み直しをしない(AI は音量が揃っている必要がない)
- 配信用 MP3 を作らない
- **半分に間引く。** 声を聞き取るのに 44.1kHz は要らないので 22.05kHz に落とします。MP3 のエンコード量がそのまま半分になり、同じ 32kbps でも1サンプルあたりに使えるビットが増えるので、むしろ聞き取りやすくなります(48kHz なら1/3にして 16kHz)
- 間引く前にローパスを3段かけて折り返しを防ぎます。12kHz を −26dB、18kHz を −80dB。子音に要る 6kHz は −1.9dB でほぼそのまま残ります

10分の素材での実測(開発機・headless Chromium):

| 入力 | これまで | ショートの経路 |
| --- | --- | --- |
| WAV | 14.0秒 | 4.5秒 |
| MP3 | 17.2秒 | 4.8秒 |

**3〜4倍**速くなります。長い動画ほど効きます。

「作成」のほうは変えていません。あちらは配信する音そのものを作るので、測るための読み直しを省けば音量が狙いから外れます。

#### 間引いても時刻はずれない

字幕は時刻がすべてなので、ここを崩すわけにいきません。ブロックをまたいで**間引きの位相を持ち越し**ています(ブロックごとに 0 に戻すと継ぎ目でサンプルが増減し、少しずつ時刻がずれる)。

検証は、1 / 5 / 11 / 23 / 47 / 89 / 137 / 179 秒(読み込みブロックの境をまたぐ位置)に印を置いた190秒の音声を通し、書き出した MP3 を鳴らし直して印の位置を測っています。結果は**8個すべてが +0.060秒**、つまり MP3 のエンコード遅延ぶんが一律に乗るだけで、**最初と最後のずれの差は 0.000秒**でした。

### 候補が「見つかりません」で止まらないようにする

AI が返す時刻の書式は毎回ぶれます。`"01:23"` のこともあれば `83`(数値の秒)、`"83"`、`"45秒"` のこともあり、終わりが動画の尺を超えていることもあります。以前はこれを厳しく弾いていたため、**AI はちゃんと答えているのに候補が全部消えて「切り出せそうな区間が見つかりませんでした」になる**ことがありました。

いまは弾かずに直します。

| 返ってきたもの | 扱い |
| --- | --- |
| `83` / `"83"` / `"1:23.4"` / `"45秒"` | すべて秒として解釈する |
| 終わりが尺を超えている | 尺に丸める |
| 終わりが無い・開始より前 | 開始+45秒とみなす |
| 90秒より長い | 90秒に切り詰める(捨てない) |
| 5秒未満 | さすがに使えないので捨てる |
| どれも解釈できなかった | 先頭60秒を「仮の候補」として1つ出す |

指示文も尺に合わせて変えます。70秒以下の動画には「**動画全体を1つの候補にして構いません**」、150秒以下には20〜60秒、それより長ければ30〜60秒と伝え、どの場合も「候補が1つも思いつかない場合でも、いちばんましな区間を必ず1つは返す」と付けます。短い動画に「30〜60秒を3つ」と言うと、AI が答えようがなくなるためです。

## 切り抜き(縦型ショート)

ポッドキャストが伸びない一番の理由は「聴くまで中身が分からない」ことです。**30〜60秒の縦型動画は、音声を聴かない人にも中身が届く唯一の入り口**なので、ここだけは手数をかけています。

生成時に、音声を聴いた AI が**それ単体で完結して面白い区間**を3つ選びます。選ばせる基準は順に「笑いが起きている」「言い切っている」「意外な事実が出る」「話が急に転換する」。前置きから始めず、冒頭2秒で引きが立つ位置を選ばせています。

候補ごとに、動画の1行目に大きく出す**見出し(hook)**と、なぜ伸びると思うかの理由が付きます。範囲は3秒単位で前後にずらせて、書き出す前に音で確認できます。

書き出しは端末内で完結します(1080×1920 / 30fps)。画面は次の要素で構成されます。

- 上部に見出し
- 中央に**字幕**(全文書き起こしを作ってあると自動で入る。ショートは音を出さずに見られることが多いので、字幕の有無で伸びが変わります)
- 下部に**実際の音量に連動する波形**と、残り時間のバー
- 背景は結果画面で読み込んだ写真(無ければ暗い単色)

### コーデックの都合

第一希望は **H.264 + AAC の MP4** です。Instagram と TikTok はこれしか受け付けません。ただし H.264 は特許の都合で載っていないブラウザがあり(開発に使った headless Chromium には無かった)、その場合は VP9 + Opus の WebM に落として、その旨を画面に出します。YouTube には上げられるので、「この端末では無理です」とだけ言って終わるよりましだからです。

### 字幕の精度

字幕は**0.5秒ずれるだけで目に見えて合わなくなります**。ずれた字幕は無いより気になるので、ここは作り直しました。

#### なぜずれるのか

原因は AI の返す時刻そのものです。AI は音声を耳で聴いて時刻を推定するので、

- **長い音声ほどずれる。** 15分の回の「12:34 から」を当てるのは、AI にとって非常に難しい
- **後ろへ行くほどずれが積み上がる。** 1行目が0.5秒、5行目が3秒ずれる、という出方をする

「近くにある発話の頭へ吸着させる」だけでは足りませんでした。3秒ずれていると**1つ隣の発話**に吸い付いてしまい、全体が1発話ぶんずれます。

#### 直し方

**1. その区間の音声だけを聴かせる**

全編を送って「12:34 から 13:20 まで」と頼むのをやめ、**その区間だけを切り出した音声**を送って「最初から最後まで書き起こして」と頼みます。AI は 0 から数えれば済むので、そもそも大きくずれません。32kbps モノラルなので60秒でも 250KB 程度です。返ってきた時刻は端末側で元の時間軸に戻します。

**2. 時刻ではなく「声の出ている場所」を物差しにする**

手元に音声があるので、50ms ごとの音量から**実際に声が出ている区間**を割り出せます。そこで、

- 「声が出ている時間だけを詰めた時計」を作る
- 字幕の各行を、**文字数の比**でその時計の上に配る(日本語は毎秒およそ7文字で一定)

こうすると、1行目は最初の発話の頭から、最後の行は最後の発話の中に必ず収まり、**誤差が後ろに溜まりません**。

**3. AI の時刻は「基準線と食い違わないときだけ」使う**

2 だけだと話速の個人差を拾えないので、AI の時刻が発話の頭の近く(±1.2秒)を指していればそこへ固定します。ただし**2 で引いた基準線から1秒以上ずれている吸着先は捨てます**。これが「1つ隣の発話に飛ぶ」を防ぐ要です。

**4. 声が止まったら消す**

次の字幕が来るまで出しっぱなしにはしません。ここには落とし穴があって、単語の切れ目や促音でも音量は一瞬落ちるため、素直に実装すると**文の途中で字幕が消えます**。**0.45秒続けて無音**になったところだけを「声が止まった」とみなしています。

#### 日本語としての読みやすさ

時刻が合っていても、切れ目が悪いと読み手はつっかえます。

- 1枚あたり**全角20文字以内**。書き起こし側にも16文字以内で区切るよう頼み、端末側でも保険をかけます
- 切る位置は **句点 → 読点 → 助詞の直後 → 字種の変わり目** の順に探します。「〜という/ことです」のような語の途中では切りません
- **行頭に句読点・小書き文字・長音符を置きません**(禁則処理)
- 「です。」だけが1枚になると読む間もなく消えるので、**6文字未満の端切れは前の行に戻します**
- 書き起こしの指示にも、つなぎ言葉と言い直しの前半を省くこと、数字は「2025年」のように書くこと、読点は息継ぎの位置に置くことを入れています

#### 検証

声の区間が分かっている合成音声で確かめています。

- AI が 2.70秒と返した字幕が、実際の発話開始 2.00秒へ寄ること
- **AI の時刻が 0.6秒ずつ累積してずれ(最大3秒)ても、6行すべてが発話の頭に 0.00秒で乗ること** — これが今回の本題
- AI が完全な無音の位置(11秒)を返しても、声のあるところへ置き直すこと
- 0.15秒の谷が繰り返し入っても、文の途中で消えないこと
- 書き出した動画で、字幕用に送るバイト数が候補用より小さいこと(=区間ぶんに絞れていること)

## この回の写真(MP3 のカバー・切り抜きの背景)

**SNS 告知画像の生成はやめました。**(3サイズのカード・AI イラスト・ChatGPT 用の注文文・文字の載せ方3種類)使われていない機能で、画面と設定を占めていたためです。

写真そのものは残しています。読み込むと2箇所で効きます。

| どこに出るか | 何のため |
| --- | --- |
| **MP3 のカバー画像** | 配信アプリの一覧に出る絵。番組名とタイトルを下の帯に載せます |
| **切り抜き動画の背景** | 縦型ショートの背景 |

入れなければ暗い単色のままで、どちらも問題なく動きます。

読み込んだ写真は端末内(IndexedDB)に控えるので、タブを切り替えても開き直しても残ります。次の回に進むと消えます(その回の情景を写したものなので、別の話に付いてしまうのを避けるため)。

検証では、**書き出した MP3 に埋まっているカバー画像を取り出して色を見ています**。写真を入れる前は暗い単色(54,46,9)、入れた後は写真の色(220,40,41)に変わります。

## 履歴の管理

- 行の 🗑 ボタンで1件ずつ削除(開かなくても消せます)
- 「音声だけ全部消す」で、タイトルや説明文を残したまま容量を空けられます
- 「履歴を全部消す」で一括削除
- 使用中の容量を常に表示

音声は直近5件まで自動保持され、それ以前は本文だけが残ります。60分の回を5本溜めると約205MBになるため、投稿後は音声を消すと容量を節約できます。

## 処理速度とメモリ

60分のステレオ収録を想定した実測(5分素材からの換算)です。

| | 変換時間 | AI送信量 | ピークメモリ |
| --- | --- | --- | --- |
| 初期実装 | 5.4分 | 55MB | 2422MB |
| 現在 | **1.2分** | **14MB** | **7MB** |

- **WASM版 LAME**(`@mediabunny/mp3-encoder`)に変更。純JSの lamejs より約3.3倍速い
- **モノラル96kbps** を既定に。トーク番組の標準で、ステレオ128kbpsより約1.7倍速くファイルも半分
- **AI送信用に32kbpsモノラルの別ファイル**を生成。配信用の音質を保ったまま送信量を4分の1に
- **ストリーミング処理**に変更。`File.slice()` でブロックごとに読み進めるため、長尺でもメモリを消費しない

初期実装は60分素材で2.4GBのメモリを要求し、スマホでは確実に落ちていました。

## バックグラウンド実行について

iOS/Android のブラウザは、他のアプリに切り替えたり画面が消えたりすると JavaScript の実行を止めます。これは Web アプリ共通の制約で、真の意味でのバックグラウンド処理は行えません。

そのため **Screen Wake Lock API** で処理中は画面が消えないようにしています。画面を点けたまま置いておけば最後まで進みます。復帰時にロックが外れることがあるため、`visibilitychange` で取り直しています。

## 音声処理

すべて端末内(Web Worker)で実行されます。設定画面で個別に ON/OFF できます。

| 処理 | 内容 | 既定 |
| --- | --- | --- |
| 低域カット | 80Hz 以下のゴロつき(空調音・机の振動)を除去 | ON |
| ノイズ低減 | 下向きエクスパンダで定常ノイズを最大 -18dB 抑制。声の区間はほぼ無加工 | ON |
| 無音カット | 1秒を超える沈黙を詰める(前後の余韻は残す) | OFF |
| 独立ノイズ低減 | 2人別マイク時にチャンネルごとに処理 | OFF |
| ラウドネス調整 | ITU-R BS.1770-4 の LUFS で測って目標へ合わせる | 常時 |
| リミッター | 先読み5msで上限 -2.0 dBFS を守る | 常時 |
| 音色合わせ | 話者どうしの周波数バランスを平均へ寄せる(±6dB) | 人ごとに分けて入れたとき |

## ラウドネス(音量)の扱い

配信プラットフォームの基準に合わせています。

| | 目標 |
| --- | --- |
| モノラル | **-19 LUFS** |
| ステレオ | **-16 LUFS** |

Apple Podcasts の基準(許容 ±1dB)です。モノラルを -19 にするのは、モノラルが左右同一のステレオとして再生されると合算で +3dB になり、ステレオ -16 と同じ聴感になるためです。

測定は **ITU-R BS.1770-4 準拠**です。K特性フィルタの係数は規格が 48kHz しか示していないため、双一次変換に周波数プリワープを掛けて任意のサンプリング周波数で導出しています(libebur128 / ffmpeg と同じ方法)。一般的な RBJ Cookbook のシェルビング式では 1kHz の利得が 0.44dB になり、規格の 0.70dB と 0.26dB ずれて測定値が狂います。

検証は規格の基準信号で行っています。`-20dBFS の 1kHz 正弦波をステレオに入れると -20.0 LUFS` という定義に対し、実測 **-19.99 LUFS**(44.1 / 48 / 96kHz すべて)。

### 目標に収束させる仕組み

単純に測って掛けるだけでは目標を外します。実測で見つかった2つの原因に対処しています。

1. **ノイズ低減は音量を下げる。** 低減前に測ると **9dB 以上**ずれました。ノイズフロアの推定に全体が必要なため、解析を2回に分けて「整音後の状態」で測っています。
2. **突発的な大音量を抑えると全体が下がる。** 笑い声のような 0.35秒の音が全体エネルギーの1/3を占めることがあり、リミッターで抑えると積分ラウドネスが **1.9dB** 下がりました。試し処理で下がる分を測って足し戻します。ゲイン後のピークが上限に届かない素材では働かないので、そのときはこのパスを省きます。

### 上限を -2.0 dBFS にしている理由

以前は -1.2 dBFS でした。「サンプル値をここまで抑えれば真のピークも -1 dBTP を超えない」という**確かめていない想定**に基づいていました。

出来上がった MP3 を復号して測り直したところ、**上限より 0.12〜0.23dB 高く**なっていました。MP3 は非可逆なので波形がそのまま戻るわけではなく、膨らみます。真のピークは **-0.97 dBTP** で、**-1 dBTP を超えていました**。0.2dB の余裕では足りません。

-1.5 でも足りませんでした。**-1.12 dBTP** まで来た回があり、余裕は 0.1dB しか残りません。-2.0 にすると実測 **-1.69〜-1.85 dBTP** で、0.7dB の余裕ができます。

下げても小さくは聞こえません。仕上がりの音量はラウドネス調整で決まるためで、実際にどちらの上限でも仕上がりは **-19.0 LUFS ちょうど**に着地しています。増えるのは瞬間的な山を抑える量だけです。

| 上限 | 届いた真のピーク | 仕上がりの音量 |
| --- | --- | --- |
| -1.2 dBFS(以前) | -0.97 dBTP ← **超過** | -19.0 LUFS |
| -1.5 dBFS | -1.12 〜 -1.48 dBTP | -19.0 LUFS |
| **-2.0 dBFS(現在)** | **-1.69 〜 -1.85 dBTP** | -19.0 LUFS |

#### 測り方そのものを先に確かめた

真のピークは `OfflineAudioContext` を高いレートで回して測っていましたが、**この方法では測れません**。ブラウザのリサンプラーは直線補間らしく、サンプル間ピークを拾いません。

答えの分かっている波形(sr/4 の正弦を45度ずらす。サンプルは ±0.707 = -3.01dBFS、波形の頂点は 1.0 = 0dBTP)で確かめると、この方法は **-3.01 dBTP** と答えました。窓付き sinc で4倍に補間する方式に替えたところ **0.000 dBTP**。上の数値はすべて後者で測っています。

足し戻しは +6dB までに制限しています。それを超えるほど抑制が必要な素材は、無理に持ち上げると抑揚が失われるため、狙いを外したまま実測値を表示します。

結果画面には**実測したラウドネス・ピーク・リミッターの働いた時間**が出るので、狙い通りかを毎回確認できます。

## MP3 のタグ

タイトル・番組名・説明文・アートワーク・チャプターを ID3v2.3 で埋め込みます。プレイヤーで番組として正しく表示され、対応アプリではチャプター送りも使えます。

- アートワークは 1400px の JPEG。3000px の PNG では 4MB を超えて音声を不必要に重くするため
- 文字コードは UTF-16。ID3v2.3 のもう一方の選択肢 ISO-8859-1 では日本語が表現できない
- チャプターは `CHAP` / `CTOC`。音声長を超える時刻は捨て、章の終わりは次の章の開始に揃える
- 検証は mutagen(Python の標準的な ID3 ライブラリ)に読ませて突き合わせています

## 実装メモ

- **Gemini Files API は `uploadType=media` を使用**。公式が案内する resumable 方式はアップロード先URLが `X-Goog-Upload-URL` ヘッダーで返るが、このヘッダーは `Access-Control-Expose-Headers` に含まれないためブラウザからは読み取れない(実 API で確認済み)。
- **アップロードは XHR**。`fetch` では送信の進捗が取れず、モバイル回線では送信が体感時間の大半を占めるため。
- **モデル名はアプリに持たない**。Google は予告より早くモデルを廃止することがあり(実際 `gemini-2.5-flash` が告知された停止日より前に 404 になった)、固定リストは必ず陳腐化する。設定画面の選択肢は `ListModels` の結果から作り、生成時に 404 が返ったら利用可能なモデルを引き直して一度だけ再試行し、成功したモデルを設定へ保存し直す。
- 音声処理は「ハイパス → ノイズ低減 → 無音カット → ゲイン → リミッター」の順。ノイズフロアとラウドネスの推定はハイパス後に行う(低域の暗騒音を含むと過大評価になる)。
- リミッターは単調キューによる先読み窓の最小値探索。ピークで割るだけの方式だと1箇所の大きな音で全体が小さくなり目標に届かない。
- 無音カットは、無音をいったん保留バッファに溜めて次に声が来たときだけ吐き出す方式。冒頭・末尾の無音も同じ仕組みで自然に切り落とせる。保留は上限フレーム数で頭打ちにしているため、何分続く無音でもメモリは増えない。
- 履歴は IndexedDB(MP3 Blob をそのまま保持するため localStorage は不可)。
- 書き起こしはメタデータと別の呼び出し。1回の出力に詰め込むと上限に当たって全体が壊れる。
- アップロード済み音声の参照(uri と期限)を履歴に持たせ、48時間以内は再送なしで作り直せるようにしている。
- Worker は ES module 形式(`worker.format: "es"`)。WASM エンコーダを動的に読み込むため、既定の IIFE ではコード分割できない。
- 入力は `BlockReader` で抽象化。WAV は `File.slice()` の直読み、それ以外は mediabunny のデコーダ。解析パスごとに先頭から読み直すため、圧縮音声では入力を開き直している。
- 変換結果は ref に保持し、生成部分を独立した関数に分けている。生成が失敗しても変換をやり直さずに再実行できるのはこのため。同じ結果を IndexedDB にも控え、アプリが落ちても復帰できるようにしている(こちらは常に1件だけ持つ)。
- 復帰時のアップロード済み参照は state 経由ではなく引数で渡す。`setUploaded` の直後は再描画前で値が反映されていないため、state を読むと送信をやり直してしまう。
- `AudioReport` は画面ではなく `lib/audio/report.ts` に置いている。中断復帰で保存する必要があり、保存側が画面のコードを参照しないようにするため。
- **Service Worker はビルド時に生成**(`sw-plugin.ts`)。ファイル名にハッシュが付くため一覧を手で書けず、また WASM エンコーダは動的 import なので、一覧に入れないと一度も変換していない端末ではオフラインで変換できない。キャッシュ名はファイル一覧のハッシュで、デプロイして中身が変われば古い世代は破棄される。ハッシュ付きの資材は再取得せず、`index.html` だけ裏で更新する。

## ロードマップ

- **v1**: WAV→MP3 変換、音量正規化、タイトル・説明文・ショーノート・チャプター・ハッシュタグ生成
- **v2**: 整音(低域カット・ノイズ低減・無音カット)、履歴保存、トーン/文字数/禁止語などのプロンプト設定、SNS告知文生成、キャンセル対応
- **v3**: WASM エンコーダとストリーミング処理による約4倍の高速化、長尺エピソードのメモリ問題の解消、残り時間の可視化、Wake Lock
- **v4**: 告知画像の生成(3サイズ)、履歴の削除・容量管理、モデル廃止への自動追従
- **v5**: 告知画像の背景に AI イラスト、ブランドカラーのアプリ全体への適用
- **v6**: BS.1770 準拠のラウドネス調整、先読みリミッター、ID3タグ(アートワーク・チャプター)
- **v7**: チャプター時刻の吸着、全文書き起こし、音声を再送せずに作り直す、生成結果の編集
- **v8**: 入力形式の拡張(MP3 / M4A / AAC など)、2人別マイク時の独立ノイズ低減、シリーズの一貫性
- **v9**: 収録の診断(位相反転・クリッピングなど)、生成だけの再試行、Service Worker によるオフライン対応
- **v10**: 中断からの復帰(変換結果を端末に控え、開き直して生成から続ける)
- **v11**: 題名を絵の中に描く経路(ChatGPT 用の注文文生成 + 画像の読み込み)
- **v12**: 混雑(503)への自動再試行
- **v13**: 告知画像の作り直し(素材の読み込みを主役に、文字の載せ方を3種類、組版の改善)
- **v14**: 画像の注文文を実写の情景に(話者の人数を反映、Gemini とも指示を共通化)
- **v15**: 切り抜き(縦型ショート動画の書き出し・字幕・波形)、MP3 のカバーに写真を反映
- **v16**: 「ショート」ページ(動画を上げると区間を自動抽出して縦型に切り出す)

## 制約・既知の注意点

- Gemini 無料枠にはレート制限があります(429 エラー時は1分ほど待って「生成だけやり直す」)
- 混雑による 503 は自動で3回まで待って投げ直します(それでも駄目なら数分待ってから再試行してください)
- モデルが廃止された場合は自動で新しいモデルに切り替わります(手動対応は不要)
- 試験版(preview / experimental)のモデルは自動では選びません。無料枠の割り当てが細く、混んでいなくても 503 や 500 を返すためです。設定で試験版を選んでいて詰まった場合は、正式版に切り替えて一度試し直します
- 429(上限)は**1分あたり**と**1日あたり**を区別して案内します。「1分待って」は前者にしか効かず、1日の枠を使い切った人が1分おきに押し続けることになるためです
- 403 を「音声の保持期限切れ」と決めつけません。キーに制限(HTTPリファラーやIPの指定)が掛かっている場合も 403 になり、そちらの人は音声を上げ直しても直りません。応答が音声の話をしているときだけ保持期限を案内し、それ以外は Google の説明をそのまま渡します
- 処理中は他のアプリに切り替えられません(ブラウザが JavaScript を止めるため)。止められた場合も変換結果は残るので、開き直せば生成から続けられます
- 入力の WAV は 16/24/32bit 整数 PCM・32bit float、モノラル/ステレオに対応。それ以外の形式は端末のデコーダに依存します
- 3チャンネル以上の音声は先頭2チャンネルのみ使います
- ピークはサンプル値で管理しています。サンプル間のピーク(真のピーク)は処理中には測っていないため、上限を **-2.0 dBFS** にして -1 dBTP に余裕を持たせています(下記)
